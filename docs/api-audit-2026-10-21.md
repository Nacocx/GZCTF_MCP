# 官方 API 对照审查 — 2026-10-21

状态：审查完成；以下为待实施的修复与能力补充，**没有修改 MCP 运行代码**。本次仅访问官方公开文档，在既有本地 Docker 夹具上复现两个问题；未修改用户远端站点、未提交答案。

## 依据与口径

用户给定的 [Scalar 页面](https://gzctf.gzti.me/scalar#description/introduction) 是文档前端；读取其 HTML 配置后取得实际加载的 [OpenAPI JSON](https://gzctf.gzti.me/openapi.json)。本次文档标注版本为 `v1`，不能等同于某个确切 GZCTF 发布版本。

抓取文件 SHA256：`e32a4d5529083cd9572749412b0b69c19685ab06fc182d46068b362365fbdff1`。同时对照当前 MCP 源码、本地 GZCTF 源码 commit `cc12f65fe9cd9eb2a94ccfcb3604a81e394e0296`，必要处查官方前端加密流程。

官方文档共 123 个 HTTP 操作；31 个 MCP 工具直接或组合调用其中 31 个操作，其余 92 个未接入。工具数与操作数相同属于巧合，例如 container_action 对应 3 个操作，预演/上题组合工具复用已有操作。未接入不自动意味着应当全部开放：用户管理、站点设置等应根据需求独立决定。

完整操作清单和复现结果保存在 [records/api-audit-2026-10-21.json](records/api-audit-2026-10-21.json)。

## 确认的正确覆盖

- `ChallengeUpdateModel` 的字段名称集合已全部覆盖：提示、题面、原始分值、难度系数、最低分比例、三血开关、提交次数、截止时间、容器资源、网络与流量捕获等均可传入。当前模型的业务校验与特殊清空语义仍有下列问题。
- 题目类型创建后不可改，创建和配置分步符合上游接口。
- Flag 提交后取得 submission ID，再查询状态；不会把提交编号当作 Accepted。
- 报名接口已有 division_id 和 invite_code；get_game 返回分组元数据，join_check 返回可加入组 ID。没有完整的管理员分组与审核流程。
- 官方时间 Schema 显示整数，但源码 DateTimeOffsetJsonConverter 同时接受 Unix 毫秒数与 ISO 时间字符串，因此现有 ISO 请求不是单凭文档即可判定的兼容性错误。响应毫秒时间未统一转换，建议在工具层明确单位。
- Token 管理接口的存在不说明业务接口接受 Bearer Token。文档未定义 securitySchemes，权限仍需结合源码 RequireAdmin/RequireUser 判断；当前题目管理控制器不允许 Token。

## 确认的问题与优先级

### A1 · P1 · 指定已有 fileHash 恢复上题会破坏附件

**复现成立，优先修复。** 在本地 GZCTF 1.9.0 Docker 上：上传文件 → 用 `attachment={attachmentType: Local, fileHash: ...}` 创建禁用题目 → 首次下载 HTTP 200 → 同一清单指定 challenge_id 恢复 → completed=true → 用全新文件名路径下载同一 hash，HTTP 404。

MCP `workflow.py` 的 attachment 阶段无条件 POST `/Attachment`；上游 `GameChallengeRepository.UpdateAttachment` 会删除旧附件及其文件引用，然后绑定传入文件。当复用同一 hash 且没有重新上传增加引用时，旧文件可能已被删除。不能把重复 POST 当成无害操作。

本次实际结果：本地临时比赛 2、题目 5；恢复前 200，恢复后 404。临时比赛已删除并确认 404。没有在用户站点重做该实验。

修复建议：在变更附件前读取当前附件，比较类型及 hash/URL，相同则跳过绑定；保存阶段与上传结果；完成后再次下载校验并读回题目。补充 static fileHash 恢复、attachmentPath 恢复、Remote 附件相同/变化的定向检查。

此前远端恢复验收只核对 Flag 不重复，附件内容校验发生在恢复之前，因此没有覆盖恢复后附件仍可下载。之前 9 项记录不能证明这一项正确。远端旧 URL 200 随后附件清理 404 的现象不能仅归因于缓存，该缺陷也可能影响原测试文件；本次不能据此断言远端当时的确切删除时点。测试资源最终不存在的清理结论已独立复核。

### A2 · P1 · 未处理开启 API 加密后的 Flag 提交

`server.py` 的 submit_flag 直接发送明文 `{flag: ...}`，从不请求 `/api/config`，也没有调用加密函数。官方 `ClientConfig` 有 apiPublicKey；源码 ConfigService.DecryptApiData 在启用 ApiEncryption 时解密请求，官方前端 GameChallengeModal 会通过 Crypto.ts 加密 Flag。

因此开启该配置时，当前明文提交路径不兼容。已有 Cookie 不能解决请求体加密问题。此结论来自源码与 MockTransport 抓取请求体，未在用户远端提交 Flag。

修复建议：读取并缓存客户端配置，提供与官方 X25519 + SHA-256 + AES-GCM 格式相同的加密适配；无 apiPublicKey 才发送明文；明确密钥变化时刷新规则。加密错误不能自动重提答案。

### A3 · P1 能力缺口 · 分组配置和报名审核不完整

官方提供 Division CRUD，含 defaultPermissions、challengeConfigs、邀请码。权限不仅控制是否报名，还决定题目可见、提交、得分、血奖、影响动态分值、总榜资格、是否审核等。当前 MCP 没有任何管理员分组 CRUD 工具，也不能配置单题分组权限。

另外缺少 GET `/api/game/{id}/participations` 与 PUT `/api/admin/participation/{id}` 对应的报名查询/审核工具。join_game 返回成功不保证已审核通过，当前工具没有统一的最终资格确认步骤。

修复建议：补充分组和权限模型及工具；按名称明确解析唯一组 ID，多个候选不得擅自选择；报名后读取参与状态，并区分 Pending/Accepted/Rejected；在本地增加公开组、邀请码组、需审核组、不可见/不可得分题的检查。

### A4 · P2 · null 不能清除截止时间，且截止时间未强制时区

MCP `ChallengeUpdate(deadline_utc=None).payload()` 发送 `{deadlineUtc: null}`。源码 `GameChallenge.Update` 将 null 当成“不更新”，只有 Unix epoch 哨兵（ToUnixTimeSeconds()==0）才清除截止时间。虽然文档文字写 null means no deadline，更新场景必须以实际实现为准。

本地真实验证：设置截止时间后，发送 null，读回数值不变；发送 `1970-01-01T00:00:00Z`，读回才变为 null。MCP 目前没有明确的 clear_deadline 操作或说明。ChallengeUpdate 也接受不带时区的时间，GameCreate 的时区校验并未复用到这里。

修复建议：提供显式清空操作并映射哨兵，更新前后读回核验；要求带时区输入并统一响应时间单位。不要把 null 同时解释为“保留”和“清空”。

### A5 · P2 · 通用错误掩盖了自动化所需的业务原因

`client.py:check_response` 不解析 RequestResponse.title/status，所有 400 都变为同一条通用错误。组邀请码不对、必须选分组、报名审核、题目缺 Flag、模板无效、容器续期尚未到窗口等原因会混在一起。

保密策略有价值，但完全丢弃业务错误使 AI 很难采取正确下一步。官方 RequestResponse.status 还可能携带业务状态，不能仅凭 HTTP 分类代替。

修复建议：结构化返回 HTTP status、脱敏和长度限制后的业务提示/业务码、是否可重试、下一步工具提示；不输出请求中的密码、Cookie、Flag。保留写操作不自动重试。

### A6 · P2 · 计分参数的业务预检不够

当前 ChallengeUpdate 接受 originalScore=-100、difficulty=-1，以及难度系数 0 和非有限数。OpenAPI 对 difficulty 和 originalScore 也没有严格数值下限，因此这是自动化层的业务校验缺口，不是声称官方 Schema 已明确禁止。

源码 GameChallenge.CalculateChallengeScore 使用 exp((1-acceptedCount)/difficulty)，负数或零会产生不符合预期的衰减行为。建议限制初始分为非负或按项目规则的正数、难度系数为有限正数，并为特殊计分需求提供明确约定。题目提示、三血开关等字段存在不等于已经验证了完整计分行为。

### A7 · P2 能力缺口 · 比赛和文件生命周期依赖测试脚本绕行

当前只有比赛创建和读取，没有修改比赛、删除比赛、海报上传、公告管理、比赛级 bloodBonus 配置，也没有文件列举与删除工具。默认隐藏的新比赛无法在创建后通过现有 MCP 工具修改 hidden。

远端测试中的比赛与附件清理使用 Python 直接调用 API，不能因此说 MCP 已提供这些管理工具。上题失败只返回阶段与题目 ID，没有可供 AI 复核的完整资源清单和显式清理工具。

修复建议：补上比赛更新/删除、文件 inventory/清理、公告和海报工具；比赛更新要考虑上游为整对象 PUT，不能直接把 ChallengeUpdate 的局部字段逻辑照搬到 GameInfoModel。清理仅作用于明确记录的本次资源，支持引用与缓存复核。

### A8 · P2 能力缺口 · PlatformProxy 容器无法直接使用

官方 ClientConfig.portMapping 可为 PlatformProxy，提供 `/api/proxy/{id}` 和 `/api/proxy/noinst/{id}` TCP over WebSocket。源码 Container.Entry 在该模式下是容器 UUID，不能当成 host:port 或普通 HTTP URL。

当前 MCP 只返回 entry，不读取 portMapping，也不提供 WebSocket 到本地 TCP 的桥接信息/工具。已有本地容器验收使用 Default 端口映射，不覆盖此场景。

修复建议：暴露容器连接类型、生命周期与代理路径；按需提供本地桥接，或返回用户可执行的明确连接步骤。先做连通性检查再把容器启动等同于 AI 能访问题目。

### A9 · P2 能力缺口 · 登录、会话和配置发现仍需人工处理

官方有 login/logout、config、captcha、powchallenge。MCP 只从环境读静态 Cookie，没有账号密码登录、验证码状态反馈或会话过期后的重新认证。核心客户端只接受完整 Cookie 头；上次站点测试中的原始 Token 补前缀与 URL 覆盖由专项脚本完成，不是通用 MCP 配置能力。

修复建议：先增加客户端配置/认证诊断和 Cookie 格式识别，再实现遵守站点验证码策略的登录工作流；账号密码仍放本地环境，不作为普通工具参数返回或记录。401 与连接目标错误应能明确区分。

### A10 · P3 能力缺口 · 批量迁移与赛务观察不完整

官方已有比赛导入/导出接口，当前只能逐清单部署；多题批处理没有总计划、逐题执行记录和持久化恢复状态。动态附件还需要逐文件上传后人工构造 Flag/hash 对应关系。导入/导出和榜单表格等为二进制接口，现有只解析 JSON 的 request 方法不能直接复用。

参赛侧缺少 Writeup 状态工具、退赛与队伍创建/邀请等完整入口；赛务侧缺少提交记录、事件、实例清单/管理员停止实例、榜单/提交表导出。应优先补与实际需求有关的部分。

## 建议实施顺序

1. 修复 A1 的附件恢复问题，并对相同 hash、清空截止时间、更新读回补充回归验证。
2. 补充 config/请求体加密、结构化错误；保持用户远端“不得答题”的限制，相关验证只在本地夹具执行。
3. 补齐分组 CRUD、权限映射、报名审核，验证多组场景。
4. 完成比赛/文件清理生命周期及认证诊断。
5. 按使用场景补 PlatformProxy、导入导出和批量持久化执行。

本报告是审查结论与开发建议，不代表上述缺口已经实现或修复。当前已有的 27 项测试证明既有覆盖通过，不足以排除新发现的两个真实行为问题。
